# ShadowPlayer

A minimalist iOS video player built for **A-B repeat playback** — ideal for
shadowing / language practice and drilling a passage over and over.

## Features

- **Pick a video**: choose videos from your photo library and play them
  (streamed by asset identifier, no file copy)
- **Recent list**: a persisted list that moves the most recently played to the top
- **A-B loop**:
  - Set the **A** start point and **B** end point; playback jumps back to A when
    it reaches B, looping indefinitely
  - **Cancel** clears the loop and continues normal playback
- **Playback controls**: play/pause and a draggable scrubber with A/B markers
- **Seek**: tap to jump 3 seconds, press-and-hold to scan continuously
  (~5x), release to stop
- **Playback speed**: 0.8x–1.2x, with natural voice pitch
- **Resume playback**: continues from where you left off
- **Per-video word list**: an inline, editable list below the video for jotting
  words while you practice; persisted per video
- **Background audio**: keeps playing (A-B loop included) when the screen is
  locked or you swipe to the home screen — the video layer detaches so audio
  continues
- **Fullscreen**: portrait by default, rotates to landscape in fullscreen
- Plays sound even when the hardware silent switch is on

## Tech stack

- SwiftUI + AVPlayer + PHPickerViewController
- iOS 16.0+

Background audio requires the `audio` background mode, declared in
`ShadowPlayer-Info.plist`. It cannot be expressed as an `INFOPLIST_KEY_*` build
setting, which is why the target uses a partial `Info.plist` alongside
`GENERATE_INFOPLIST_FILE`.

## Running

Open `ShadowPlayer.xcodeproj` in Xcode, select your own Team under
**Signing & Capabilities**, and run on a physical device. Picture in Picture is
unreliable in the Simulator, so test it on a real device.

## App icon

The app icon is generated by `scripts/make_icon.py` (requires Pillow) and
written to `ShadowPlayer/Assets.xcassets/AppIcon.appiconset/`.

## Releasing to TestFlight

Every push to `master`, or a manual run of the **TestFlight** workflow, archives
the app, signs it automatically with an App Store Connect API key, and uploads
it to TestFlight (`.github/workflows/testflight.yml` → `scripts/ci/testflight.sh`).
It never submits for review. The build number is the run number plus the
`BUILD_NUMBER_OFFSET` repository variable (default 4). The version comes from
`MARKETING_VERSION` in the project, so bump it there for a new release.
Required secrets: `ASC_KEY_ID`, `ASC_ISSUER_ID`, and `ASC_KEY_P8` (the `.p8` file's text, or base64 of it).

## Submitting for App Store review

Once a TestFlight build has finished processing, the **Submit for review**
workflow (`.github/workflows/submit-review.yml` → `scripts/ci/submit-review.py`)
attaches it to the App Store version, fills What's New and review notes from
`submissions/<version>/`, and submits it. It only runs by hand.

From the GitHub phone app: repository → **Actions** → **Submit for review** →
**Run workflow**, then fill in:

- **version**: e.g. `1.4`
- **build**: leave empty for the newest processed build
- **release_type**: `manual` (release yourself after approval) or `automatic`
- **dry_run**: keep on for the first run; it only reads and prints the plan
- **confirm**: type `SUBMIT`

Check the dry-run log, then run again with dry_run off. Screenshots, privacy
answers, and other version-level settings must already be in App Store Connect;
if anything is missing the run stops and prints Apple's error.
